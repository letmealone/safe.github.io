개발계획 문서에 근거한 안전워치 UX 개편 자문

검토일: 2026-09-15
역할: 문서 분석 및 개편 방향 자문. 실사이트 탐색은 주 에이전트가 별도로 수행했다.
자료: 사용자 제공 「20260903 국토부 중간점검_안전AI_fin.pdf」, 전체 28쪽. 아래 페이지는 PDF 파일의 페이지 번호이며, 본문 슬라이드 번호와 같다. 전체 텍스트와 주요 도식·표·목업을 렌더링하여 대조했다.

1. 결론

개편의 중심 단위는 ‘건축물에서 발생한 업무 건’이어야 한다. 공무원은 담당 업무와 처리할 대상을, 전문기관은 수행 중인 점검과 미완료 항목을 먼저 확인하고, 그 업무에 필요한 지도·BIM·AI·보고서를 이어서 사용하게 구성하는 것이 맞다.

이 방향은 연구계획과 부합한다. 자료 19쪽은 행정업무, 서비스 기능, R&D 기술을 별도 층으로 구분한다. 행정업무는 관리계획→점검→진단→평가→보강→해체로 정리되어 있다. 따라서 실제 사용자 메뉴도 사용자 업무를 기준으로 구성하고, R&D 기술은 각 업무에서 필요한 도구로 연결할 근거가 충분하다.

동시에 지도는 중요하다. 자료 13~15쪽은 개별 건축물과 지역을 연결하여 광역 후보를 선별하고 반복 추적하는 것을 주요 가치로 제시한다. ‘일상 처리 업무’와 ‘관할 현황·대상 선별’이라는 두 시작 경로를 제공하는 구성이 적합하다. 모든 사용자를 지도 첫 화면으로 보내는 선택이 업무 적합성을 떨어뜨린다는 해석이지, 지도 자체가 불필요하다는 의미는 아니다.

2. 문서의 시점과 사업 범위

현재 안전워치와 후속 AI 사업을 구분해야 한다

구분 문서 근거 UX 평가·제안에 적용할 기준
현재 안전워치 선행사업 5쪽: 2022~2026년. 27쪽: 지자체 디지털 안전워치 개발시스템, 고양시 테스트베드, 서울시 sBIM 기능 제공 협의 실제 존재하는 업무지원·표·현장점검·BIM·AI 탐지 기능의 발견성과 연결성을 평가한다.
후속 위험예측 AI 본사업 5쪽: 2027~2031년. 8쪽: 선행사업 중복 최소화. 9~11쪽: 정보 예측, 진단·평가, BLCM 연계·실증 현재 사이트에서 없다고 결함으로 단정하지 않는다. 단계별 확장안으로 제시한다.
현재 공무원 지원 4종 27쪽: sBIM 관리·시각화, 안전관리 업무지원, LLM 스마트 검색, 조적조 간략 내진성능평가 이미 있는 기능을 사용자 업무에 재배치하는 것이 우선이다.
현재 기관·거주자 지원 3종 27쪽: AI 구조점검, 소규모건축물 현장점검·결함매핑, 민간 자가점검 전문기관의 점검 업무와 거주자의 자가점검은 서로 다른 입구·설명·완료 기준을 가진다.
후속 서비스 목표 7·27쪽: 정부·지자체 10종, 기관·거주자 6종 메뉴 16개를 그대로 만드는 근거가 아니다. 서비스가 해결하는 사용자 과업으로 묶는다.
후속 AI 범위 25~26쪽: 정보 종류·대상 구조 확대, 위험징후·위험선별·진단·평가·보수보강 현재 간략평가, 현장 관찰, 후속 AI 예측 결과를 같은 확정 등급처럼 표시하지 않는다.

주의할 해석: 26쪽의 법령별 점검 대체·보조라는 표현은 연구계획의 적용 목표다. 그 문구만으로 현행 법적 대체 가능성이나 현재 서비스의 효력을 확정할 수 없다. 7·14·21·22쪽의 정확도·비용·시간 수치도 목표·사업화 가정의 맥락으로 읽어야 하며, 이번 실제 UX 탐색에서 검증한 성능 수치가 아니다.

3. 현재 플랫폼의 위치: 실무 공간과 Open Lab

17쪽은 BLCM 운영시스템에 연구 결과를 바로 적용할 때 서비스 구축·기능 검증, 콘텐츠 품질·안정성, 3D 기반 정보체계의 제약이 있다고 설명한다. 이어 BLCM 기능과 AI 콘텐츠를 개발·시범적용·검증할 Open Lab을 제안한다. 18쪽은 그 Open Lab을 안전워치 플랫폼으로 표시한다.

이는 현재 화면의 기술 중심 구성을 설명하는 배경이 될 수 있다. 연구 시연·모델 검증·데이터 운영과 공무원·기관의 일상 업무가 같은 화면에 섞이면, 주 사용자가 시스템의 구성 원리를 이해해야 자기 일을 찾게 된다.

권고 구조는 다음과 같다.

  1. 업무 공간: 내 업무, 건축물·점검 목록, 현장점검, 점검결과·보고서, 관할 현황·선별. 사용자의 권한과 실제 제공 범위에 맞춘다.
  2. 실증·데이터 운영 공간: 모델·레이어 관리, API, 데이터 검증, 실험 콘텐츠와 성능 검증. 해당 담당자에게 노출한다.
  3. 두 공간은 동일한 건축물 식별정보와 업무 건을 연결한다. 실증자료의 적용 여부, 검증 상태, 생성 기준일을 업무 화면에서 필요한 만큼 확인하게 한다.

이것은 사이트를 둘로 새로 만드는 제안이 아니다. 기존 화면의 진입점·권한별 노출·공통 상세 맥락을 정리하는 수준부터 시작할 수 있다. 문서가 최종 운영 조직이나 제품 구성을 확정한 것은 아니므로, 이 분리는 문서에 근거한 UX 제안이다.

4. 최적의 사용자 시나리오

A. 지자체 담당자의 일상 업무: 점검기한·처리현황 확인

계기: 출근 후 담당 대상 중 오늘 확인할 점검과 미완료 업무를 파악한다.

권장 흐름

  1. 기관·관할·담당 역할이 표시된 내 업무에 진입한다.
  2. 기한 임박/초과, 기관 확인 필요, 보완 진행 등 실제로 확인 가능한 상태를 누르면 같은 조건의 목록이 열린다.
  3. 목록에서 건축물·주소·점검유형·회차·기한·현재 상태·담당기관을 확인한다.
  4. 한 업무 건을 열면 상단에 어느 건축물의 어떤 점검인지가 지속된다. 현황, 기관, 과거 이력, 관련 증거, 지도·BIM을 같은 맥락에서 본다.
  5. 현재 서비스에서 관리하는 자료의 확인·정리와 외부 법정 시스템에서 진행할 업무를 구분하여 안내한다.

핵심 판단: 정기점검 목록에서 사용자가 원하는 것은 건물을 찾는 일 이후의 ‘그래서 어떤 상태이며 무엇을 확인해야 하는가’이다. 목록의 모든 행을 지도 패널로 열어야 하면 같은 건축물을 반복 탐색하는 부담이 생긴다.

범위: 기존 관리자 표·필터·엑셀·이력·기관정보의 재배치가 우선이다. BLCM 실거래 접수·승인 상태를 자동 갱신하는 단계는 별도 연계 확인이 필요하다.

B. 전문기관의 기존 점검건 수행: 현장 확인에서 보고서까지

계기: 기관 담당자가 배정받았거나 수행 중인 건축물의 지난 점검 내용과 이번 점검의 미완료 항목을 확인한다.

권장 흐름

  1. 진행 중인 점검에서 건축물·점검유형·회차·현장일·작성 상태를 보고 업무를 선택한다.
  2. 이번 점검과 지난 점검의 범위를 명확히 표시한다. 지난 결함 사진·부위·측정값을 먼저 확인한다.
  3. 현장 조사, 결함 목록, 시설현황, 관련 점검표를 기존 SSIB 화면과 연결하여 연속적으로 사용할 수 있게 한다.
  4. AI 탐지 결과가 있으면 원본 증거와 담당자 확인 상태를 함께 본다. 탐지 결과와 확인된 결함의 수를 구분한다.
  5. 보고서 준비 화면에서 미입력 설명·누락 사진·산정 불가 항목 등 현재 확인할 부분으로 바로 이동한다.
  6. 작성된 결과와 기존 다운로드 기능을 이용하고, 법정 보고는 실제 연계 수준에 맞게 이어 간다.

유지할 강점: 주 에이전트가 확인한 기존 SSIB 보고서·PDF/데이터셋 다운로드, 회차별 결함 사진·수치 비교, BIM 위치 확인을 적극 활용한다. 동일 기능의 신규 개발을 권할 이유가 없다.

핵심 보완: 현장조사 완료, 보고서 작성 완료, 제출 완료, BIM 연계 완료는 서로 다른 의미다. 공통 상세에서 이 구분을 유지하고, 한 가지 완료 표시가 전체 업무의 종료처럼 보이지 않게 해야 한다.

추가 관찰 반영: AI 탐지에는 이미 1차 탐지→오탐 검토→최종 추출 단계와 사진·모델 결과가 있다. 신규 검토 절차를 다시 만드는 제안보다, 기존 결과를 현장 위치·검토 상태·측정 단위·근거 중심으로 읽게 하는 것이 우선이다. IFC 영문 부재명·GUID 같은 기술 식별자는 추적에 필요한 상세 정보로 유지한다.

문서 근거: 13·21쪽은 BIM을 객체정보와 반복 이력 관리에 사용한다. 16쪽은 비전 AI 결과를 전문가 확인용 점검정보로 만들고, 후속 평가·의사결정에서 근거와 검증을 연결한다. 27쪽은 현장점검·결함매핑을 현재 제공 기능으로 구분한다.

전문기관 역할의 구분: 사용자가 안전진단 전문기관도 핵심 타깃으로 명시했으므로, 현재는 해당 담당자의 자료 검토·현장 증거·결함 비교·보고 준비 경험을 우선 개선하고, 후속 정밀진단·성능평가를 별도 업무 유형으로 수용한다. 현재 점검 기능 전체를 ‘안전진단’으로 이름만 바꾸는 것은 업무 의미를 흐릴 수 있다.

C. 지자체의 관할 위험 후보 선별: 지도가 중심인 업무

계기: 제한된 점검 자원을 어느 건축물에 우선 배분할지 검토한다.

권장 흐름

  1. 관할 현황·대상 선별을 열어 조사 대상 범위, 기준일, 자료 확보범위를 확인한다.
  2. 구조·화재 등 평가 종류와 선별 조건을 선택한다. 지도와 목록은 동일한 대상 집합·총수를 표시한다.
  3. 후보를 선택하면 왜 포함됐는지가 보인다. 사용한 자료, 관찰된 징후, 과거 점검 이력, 자료가 없는 항목을 한 화면에서 확인한다.
  4. 사진·현장기록·필요한 BIM을 이용해 후보를 검토한다. 주소와 건축물 매칭이 불확실한 경우 그 사실을 먼저 식별한다.
  5. 권한 있는 담당자가 현장확인 대상, 추가자료 필요, 추적관찰, 제외 등 다음 단계와 이유를 남기는 업무를 설계한다.
  6. 현장확인 대상으로 선정되면 동일 건축물에서 점검 업무로 연결된다. 이후 결과가 후보·추적 목록으로 돌아온다.

이 시나리오의 핵심: 위험도 시각화 다음에 담당자의 판단과 후속 확인이 이어져야 한다. 그래야 지도가 행정과 현장 업무의 시작 도구가 된다.

반복 흐름: 15쪽은 저·중위험에서도 위험징후 탐지와 자가점검을 통해 재검토 대상으로 들어오며, 점검·진단 후에도 추적관리로 돌아오는 화살표를 표시한다. 모든 건축물이 한 번만 선별→점검→진단→보강으로 이동하는 단일 진행표로 표현하면 이 반복성이 사라진다.

구현 구분: 현재 존재하는 지도·평가 결과·건축물 이력을 연결하는 작업은 재배치다. 후보 검토 사유, 선정 결정, 담당자·일정·추적 목록은 신규 업무설계가 될 수 있다. 광역 AI 위험징후 모델과 자동화된 정밀진단을 추가하는 것은 후속 연구 범위다.

D. 실증·데이터 담당자의 자료 준비·검증

계기: 건축물대장, 점검표, BIM, 현장 자료가 같은 건축물을 가리키는지 검증하고 연계 누락을 해결한다.

  1. 실증·데이터 운영 공간에서 자료 도입·검증 결과를 확인한다.
  2. 식별 실패나 중복·불일치를 건축물 단위로 분류한다.
  3. 건축물 식별자, 주소, 자료 생성일, 출처를 대조한다.
  4. 업무 사용 가능 상태와 미검증 상태를 구분하여 사용자 화면에 전달한다.

문서 근거: 11쪽은 DB 표준·매핑·품질검증·BIM-GIS 통합을 명시하고, 17쪽은 PK·DB·레이어·BIM 기반 인프라 연계가 과제임을 밝힌다. 데이터 품질은 개발자만의 문제가 아니다. 잘못 연결된 자료는 사용자의 업무 판단을 흐리므로, 업무 화면에는 그 의미를 이해할 수 있는 상태를 제공해야 한다.

추가 관찰 반영: 현재 시스템에는 식별 실패 목록과 대장·건축HUB 검색·직접등록을 이용한 복구 UI가 이미 있다. 이를 ‘오류복구 기능 없음’으로 평가하지 않는다. 확인이 필요한 자료를 담당자의 업무 홈에 올리고 기존 복구 화면으로 연결하는 개선이 적합하다. 지도·관리자 목록·기관 목록의 건수가 다른 경우에는 조회 범위·권한·기준일을 우선 확인한다. 그 차이만으로 데이터 손실이나 집계 오류를 단정할 수 없다.

5. 화면 구조 권고

첫 화면

공무원: 기관·관할 표시 → 바로 처리/확인할 업무 목록 → 기한·상태 필터 → 최근 업무 → 관할 현황·선별 바로가기.

전문기관: 진행 중인 점검 목록 → 보완·미완료 항목 → 현장 예정/최근 작업 → 지난 점검 비교.

건물 수·지도 면적·모델 수 같은 총량은 보조 현황이다. 총량 카드만 있는 대시보드는 사용자가 처리할 일을 찾는 문제를 충분히 해결하지 못한다.

공통 상세의 기본 단위

건축물과 업무 건을 구분한다. 한 건축물에는 정기점검, 소규모 점검, 민원·자가점검, 위험후보 검토, 보수보강 등 여러 이력이 생길 수 있다. 건축물 상세를 열면 현재 선택된 점검유형·회차가 분명히 보이고, 다른 이력으로 전환해도 건축물의 맥락을 유지한다.

예시 구성:

  • 고정 제목: 건축물명·주소·동 / 점검유형·회차 / 담당기관 / 기준일.
  • 업무 요약: 기한, 절차 상태, 자료 준비 상태, 다음 확인 항목.
  • 업무에 따른 내용: 점검내용·결함, 보고서, 과거 이력, 담당기관.
  • 보조 도구: 위치·주변 지도, 3D·결함 위치, AI 탐지 근거, 원천자료.

모든 법령·점검유형에 동일한 화면과 상태를 강제하지 않는다. 공통 식별·탐색 구조를 공유하고, 해당 업무에 필요한 절차·항목을 적용한다.

상태를 나눠 표현할 것

상태 차원 예시 혼동 시 발생하는 UX 문제
일정 기한 내, 임박, 초과 초과라는 이유만으로 제출 여부나 안전성까지 판단하게 됨
점검·보고 절차 작성 중, 제출, 검토, 보완, 완료 내부 작성 상태와 외부 접수·승인 상태를 혼동
기술적 관찰·평가 결함 있음, 해당 없음, 미점검, 평가 결과 자료 없음이 양호나 결함 소멸로 읽힘
자료·연계 준비 사진 등록, 모델 연계, 보고서 누락, 식별 확인 필요 BIM 연계 완료가 업무 전체 완료로 보임
근거의 성격 현장 확인, 과거 문서, 추정값, AI 후보 추정과 확인 사실을 같은 확실성으로 판단

새 상태 이름은 실제 운영 절차와 상태 전이표를 확인한 뒤 확정해야 한다. 위 표는 구분 원칙이다.

6. BLCM 연계에 관한 문서의 약속과 미확인 부분

자료에서 확인되는 범위

  • 11쪽: 정보체계 표준·매핑, 데이터 연계·운영, 품질검증, BIM-GIS 통합, UI/UX 기능 설계.
  • 17쪽: BLCM 연계 시 운영계 서비스·품질·검증 제약, 3D 기반 정보체계 필요, Open Lab 시범적용.
  • 18쪽: 세움터 설계도서와 정부·지자체 레거시 데이터를 활용하는 개념적 흐름.
  • 19쪽: 다양한 행정·외부 자료, 행정업무, 서비스, 연구기술을 연결하는 기능 구조.
  • 20쪽: 단계별 BLCM 연계·실증 및 POC.
  • 22쪽: 핵심 모듈을 BLCM에 직접 이관하는 공공 이관·실증 사업화 시나리오.

이 문서만으로 확인되지 않는 사항

  • 현재 안전워치가 BLCM 데이터를 어떤 API·파일·운영 절차로 얼마나 자주 취득하는지.
  • 조회가 가능한 정보의 범위, 점검회차·동·대장 식별자 매핑의 현재 계약과 구현.
  • 안전워치/SSIB에서 작성한 자료의 BLCM 업로드·접수·승인·반려·보완 결과 반환 여부.
  • 전자서명, 기관·직원 권한, SSO, 첨부파일 규격, 법정 기록의 최종 관리 주체.
  • 수정 충돌·정정·부분 실패·재전송·재시도와 감사 이력의 운영 기준.

따라서 ‘BLCM과 동일한 업무 언어로 정리’와 ‘BLCM 거래를 직접 수행’은 개발 난이도와 전제조건이 다르다. 전자는 현재 개편의 기준으로 채택할 수 있고, 후자는 인터페이스·권한·운영 책임을 확인한 뒤 구체화해야 한다.

8. 검증할 과제

연구의 기술 성능과 사용자 경험 성능을 각각 검증한다. 문서 20쪽의 단위기술 검증→지역단위 통합 실증→BLCM 연계 실증 단계는 UX 검증을 넣기에도 적합하다.

권장 실무 과제:

  1. 공무원: 관할 내 특정 조건의 미완료 점검을 찾아 현재 상태와 다음 확인 대상을 설명한다.
  2. 전문기관: 지난 점검에서 지적된 부재의 사진·수치를 찾아 이번 점검과 비교한다.
  3. 전문기관: 보고서를 완성하기 위해 남은 항목을 찾아 정확히 이동한다.
  4. 공무원: 위험 후보의 선정 근거와 미확인 정보를 보고 현장확인 필요성을 검토한다.
  5. 양쪽: BIM 연계 완료/현장 완료/보고서 작성 중이 동시에 보이는 건의 실제 완료 범위를 설명한다.

측정할 항목은 업무 시작 지점 찾기, 올바른 건축물·회차 선택, 현재 상태 해석, 필요한 증거 찾기, 미완료 항목 식별, 시스템 간 이동 후 맥락 유지다. 수행 시간, 잘못 선택한 건수, 되돌아가기 횟수, 중복 탐색, 도움 요청, 잘못된 완료 판단을 기록한다. 목표 수치는 사용자 테스트의 현행 기준값을 확보한 뒤 정한다.
